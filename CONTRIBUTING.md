# Как участвовать в разработке

## Стратегия ветвления

Мы используем **GitHub Flow**.

**Почему именно он**: нас трое, в эксплуатации всегда одна версия сервиса, а работа нарезана вертикальными срезами длиной в неделю (см. [docs/roadmap.md](docs/roadmap.md)). Отдельные ветки `develop`, `release` и `hotfix` из GitFlow нужны, когда параллельно поддерживаются несколько версий и релизы долгие, — у нас этого нет, и лишние ветки только увеличили бы число слияний и конфликтов. Главный риск для нас — долгоживущие ветки, поэтому ветка живёт не дольше одной задачи и одной недели.

- `main` — всегда рабочая, защищена от прямой записи
- Ветка под задачу создаётся от `main`, живёт не дольше недели
- Слияние — только через запрос на слияние с ревью и зелёным конвейером
- Способ слияния — squash; ветка удаляется после слияния

### Именование веток

`<тип>/SCRUM-<номер>-<краткое-описание-через-дефис>`

Номер задачи из Jira нужен, чтобы ветка и запрос связались с задачей. Для работы без задачи номер можно опустить.

| Тип | Когда |
|---|---|
| `feat/` | Новая возможность |
| `fix/` | Исправление |
| `refactor/` | Изменение без смены поведения |
| `docs/` | Документация |
| `chore/` | Рутина, конфигурация |

Примеры: `feat/SCRUM-12-poisk-hostov`, `docs/SCRUM-9-cjm`, `chore/repo-setup`

## Формат коммитов

`<тип>(<область>): <краткое описание>`

Типы: `feat`, `fix`, `refactor`, `docs`, `test`, `chore`.

Области соответствуют контекстам проекта: `hosts`, `pets`, `booking`, `reports`, `ci`, `docs`.

| Так не надо | Так надо |
|---|---|
| `фикс` | `fix(booking): не создавать бронь сверх вместимости хоста` |
| `работа` | `feat(hosts): очередь заявок для модератора` |
| `.` | `docs: критерии приёмки для S5` |

Проверка: по сообщению понятно, что изменилось, без открытия разницы. Если тип назвать не получается — в коммите смешаны разные изменения, его надо разделить.

## Требования к запросу на слияние

Заголовок — по формату коммита. Описание заполняется по шаблону, обязательно:

- **Что изменено** — смысл, а не пересказ разницы
- **Почему** — задача в Jira (SCRUM-xx) или причина
- **Как проверить** — шаги для ревьюера

Размер: ориентир до 400 строк изменений. Больше — режьте по сценариям.

## Что проверяется при ревью

В этом порядке:

1. Замысел — решает ли изменение заявленную задачу
2. Корректность — логика, граничные случаи, отказы
3. Тесты — упадёт ли тест, если сломать код
4. Безопасность — валидация, секреты, права доступа
5. Читаемость — будет ли понятно через полгода
6. Стиль — проверяется машиной (хуки и конвейер), не человеком

### Формат комментариев

Помечайте тип замечания:

| Метка | Смысл |
|---|---|
| `praise:` | Удачное решение |
| `question:` | Вопрос на понимание |
| `suggestion:` | Предложение; автор вправе не согласиться с аргументом |
| `issue:` | Проблема, которую нужно исправить до слияния |
| `nit:` | Придирка, можно проигнорировать |

Замечание относится к коду, а не к автору. Хороший комментарий: что не так → к чему приведёт → вариант решения. Одобрение без единого комментария по существу ревью не считается.

### Время ответа

Ревью даётся в течение суток. Дольше — ветка расходится с основной.

## Определение завершённости

Задача считается сделанной, если (полная версия — в [docs/process.md](docs/process.md)):

- [ ] Изменение влито в основную ветку через запрос на слияние
- [ ] Запрос прошёл ревью другого участника, есть содержательные комментарии или явное «проверил такие-то сценарии»
- [ ] Конвейер проверок зелёный
- [ ] Написаны тесты на критерии приёмки задачи; они проходят в конвейере
- [ ] Документация обновлена: README или соответствующий файл в `docs/`; в запросе указано, какой именно
- [ ] Добавлена запись в `CHANGELOG.md`
- [ ] Изменение проверено на чистом окружении (не только «у меня работает»)
- [ ] Новое упрощение, если оно принято осознанно, записано как технический долг со сроком возврата
