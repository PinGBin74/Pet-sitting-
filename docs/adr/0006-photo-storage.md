# 6. Фотографии на файловом томе за портом PhotoStorage, отдача через API

## Контекст

Хост прикладывает фото к профилю (`FR-01`) и к отчётам о питомце (`FR-07`); владелец смотрит отчёты (`FR-08`). Фото — основной объём данных системы: снимок с телефона — 3–8 МБ, база с бронями и профилями на порядки меньше.

Нужно решить, где хранить файлы фото и как их отдавать, чтобы фото отчёта видели только стороны брони (`NFR-06`), а файлы переживали пересоздание контейнера сервиса.

## Движущие факторы

- `NFR-06`: доступ к фото отчёта — только владельцу и хосту брони; файлы сохраняются при пересоздании контейнера; до 10 МБ на файл
- `NFR-02`: проверка прав на сервере, чужой объект — `404`
- `C-04`: команда из трёх человек — каждая новая служба стоит эксплуатации
- `C-05`: развёртывание через Compose
- `C-06`: внешние платные службы не используются — облачное хранилище исключено
- `NFR-05`: тесты предметной логики без внешних средств — хранилище должно подменяться в тестах
- `NFR-01`: время ответа поиска — **не различает варианты**: в ответе поиска только ссылки на фото, сами файлы отдаются отдельными запросами

## Рассмотренные варианты

| Вариант | За | Против |
|---|---|---|
| Файлы в PostgreSQL (`bytea`) | Файл и запись отчёта в одной транзакции; одна резервная копия | База разрастается в сотни раз; резервное копирование и миграции замедляются; каждый просмотр фото нагружает базу |
| **Файловый том сервиса за портом `PhotoStorage`, отдача через API после проверки прав** | Нет новой службы; проверка прав — тем же кодом, что для брони; том переживает пересоздание контейнера; в тестах порт подменяется памятью | Файлы проходят через процесс API; том привязан к одной машине; резервная копия тома делается отдельно от базы |
| S3-совместимое хранилище в Compose (MinIO, Garage) с подписанными ссылками | Отдача файлов мимо API; путь к облачному хранилищу без изменений кода | Новая служба в окружении; второй механизм доступа — подписанные ссылки со сроком, которые нельзя отозвать и легко переслать; у MinIO менялись условия поставки сборок сообщества |

## Решение

Файлы фото хранятся на **именованном томе** контейнера `api` под случайными именами; в базе — только метаданные (идентификатор, владелец, тип, размер, ссылка на отчёт или профиль). Доступ к файлам — через порт `ports/photo_storage.py`; реализация в `adapters/` — файловая система.

Фото отдаются операцией `GET /v1/photos/{id}` после той же проверки прав, что для брони: фото отчёта — сторонам брони, фото профиля — всем, если хост проверен. Тип и размер проверяются до записи на диск по содержимому файла, а не по расширению (`NFR-06`).

**Определяющий довод** — `NFR-06` вместе с `C-04`: права на фото совпадают с правами на бронь, и проверка одним кодом исключает расхождение двух механизмов доступа; при этом в окружении не появляется новая служба.

## Последствия

**Положительные.** Одна модель прав для броней и фото. Окружение не прирастает службой. Порт `PhotoStorage` позволяет перейти на S3-совместимое хранилище заменой адаптера, без изменения предметной логики.

**Отрицательные.** Отдача фото занимает процесс API: всплеск просмотров отчётов замедляет остальные запросы. Масштабировать сервис на несколько машин нельзя, пока фото на локальном томе. Резервная копия тома делается отдельно от базы — возможны записи о фото без файла после восстановления. При удалении отчёта файл нужно удалять отдельным шагом, иначе остаются «сироты».

**Что пересмотрит решение.** Второй экземпляр сервиса API; объём фото, при котором отдача через API заметно влияет на `NFR-01`; появление бесплатного или выделенного вузом объектного хранилища.
