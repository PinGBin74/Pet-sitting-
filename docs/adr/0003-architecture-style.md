# 3. Модульный монолит с гексагональным устройством

## Контекст

Главное правило основного контекста — вместимость хоста не превышается при подтверждении брони — требует согласованно читать брони хоста и записывать новое состояние брони.

## Движущие факторы

- `C-04`: команда из трёх человек, один семестр
- `C-05`: развёртывание через Compose, оркестрация не применяется
- `NFR-05`: прогон тестов не дольше 60 секунд, предметная логика проверяется без базы и сети, установка не более пяти команд
- `NFR-04`: подтверждённые брони сохраняются при перезапуске — согласованность данных проще обеспечить одной базой
- `FR-06`: подтверждение не сверх вместимости — проверка и запись в одной транзакции возможны только при общей базе Бронирования и Хостов
- `NFR-01`: 95 % поисков не дольше 300 мс при 100 хостах — **не различает варианты**: при таком объёме все подходят

## Рассмотренные варианты

| Вариант | За | Против |
|---|---|---|
| **Модульный монолит, внутри гексагональное устройство** | Одно развёртывание; проверка вместимости и запись брони в одной транзакции; предметная логика проверяется без внешних средств; модули по контекстам готовят возможное разделение | Границы поддерживаются проверкой в конвейере, а не техническим барьером: их можно нарушить одним импортом |
| Монолит без явных границ | Меньше файлов и уровней; быстрее писать первые обработчики | Через два месяца контексты смешиваются; предметная логика перестаёт проверяться без базы — `NFR-05` не выполняется |
| Микросервисы: службы хостов, броней, отчётов, оповещений | Независимые выпуски и масштабирование; отказ отчётов не задевает брони | Четыре конвейера и четыре базы; вместимость хоста живёт в одной службе, а брони в другой — согласованность при подтверждении требует распределённой транзакции или саги. При `C-04` неисполнимо |
| Монолит плюс бессерверные функции для оповещений и обработки фото | Оповещения и фото масштабируются сами | Внешняя платформа — против `C-06`; локальная разработка и `C-05` усложняются |

## Решение

**Модульный монолит с гексагональным устройством внутри.** Одно приложение, одна база данных, явные границы между предметной областью, интерфейсами и адаптерами. Контексты — модули внутри `src/petsitting/domain/`: `booking`, `hosts`, `stay`, `members`. Обработчик событий — отдельный процесс того же кода и той же базы: это разделение по способу запуска, а не по данным, и микросервисной систему не делает.

**Определяющий довод** — `C-04` вместе с `FR-06`. Независимость служб, за которую платят распределёнными отказами, команде из трёх человек не даёт ничего: выпускать независимо нечего и некому. А главное правило основного контекста — вместимость при подтверждении — в одной базе проверяется одной транзакцией, а между службами требует саги.

Границы поддерживаются правилами и проверкой конвейером (задание `boundaries`, включается вместе с первым кодом):

- `src/petsitting/domain/` не импортирует каркас, драйвер базы и клиент HTTP — должно давать пустой результат:
  `grep -rE "fastapi|sqlalchemy|asyncpg|httpx" src/petsitting/domain`
- модули контекстов не импортируют друг друга; обмен — идентификаторами и значениями через `services/` — должно давать пустой результат:
  `grep -rE "petsitting\.domain\.(hosts|stay|members)" src/petsitting/domain/booking` и аналогично для остальных модулей.

## Последствия

**Положительные.** Одно развёртывание, одна база, согласованность в транзакции. Предметная логика проверяется без внешних средств — набор тестов остаётся быстрым (`NFR-05`). Модули по контекстам дают путь к разделению, если оно когда-нибудь понадобится.

**Отрицательные.** Все части выпускаются вместе: ошибка в модуле отчётов останавливает выпуск исправления в бронях. Масштабирование — только целым приложением: всплеск загрузок фото нагружает тот же процесс, что обслуживает поиск. Границы обеспечены проверкой, которую можно обойти или отключить; косвенные зависимости через третий модуль `grep` не ловит.

**Что пересмотрит решение.** Появление второй команды, работающей над системой независимо; требование разной частоты выпуска для разных частей; нагрузка, при которой одна часть — например, загрузка и отдача фото — требует в разы больше ресурсов, чем остальные.
