# Ресурсы и операции API

Перечень составлен **до** описания OpenAPI и до кода: по каждому функциональному требованию — ресурс, операция, коды ответов и роль. Коды ответов взяты из критериев приёмки в [`../user-story-map.md`](../user-story-map.md).

Все пути — с префиксом версии `/v1`. Ошибки — в едином формате `application/problem+json`

**Роли**: «все» — без маркера; «пользователь» — любой вошедший; «владелец брони», «хост брони» — сторона конкретной брони, проверяется на сервере (ADR-0004); `moderator` — роль в маркере.

## Перечень

|---|---|---|---|---|

| `FR-03` карточка питомца (S3) | `pets` | `POST /v1/pets` | `201`; `422` вес ≤ 0, дата прививки в будущем | пользователь |

| `FR-07` фотоотчёт (S7) | `bookings/{id}/reports` | `POST`, `multipart/form-data` | `201`; `409` бронь не активна (S7 сц. 2); `413`; `415` не изображение (S7 сц. 3); `404` | хост брони |
| `FR-08` отчёты по брони (S8) | `bookings/{id}/reports` | `GET` — новые сверху | `200`, в том числе пустой список (S8 сц. 2); `404` чужая бронь (S8 сц. 3) | владелец брони, хост брони |

| `FR-10` отзыв (S10) | `bookings/{id}/review` | `POST` | `201`; `409` бронь не завершена (S10 сц. 2) или отзыв уже есть (S10 сц. 3); `422` оценка вне 1–5 | владелец брони |
| `FR-10` отзывы о хосте (S10) | `hosts/{id}/reviews` | `GET` | `200`; `404` хост не проверен | все |
| `NFR-02` регистрация | `users` | `POST /v1/users` | `201`; `409` адрес уже занят; `422` | все |
| `NFR-02` вход | `auth/token` | `POST` | `200`; `401` | все |
| `NFR-02` продление | `auth/refresh` | `POST` — обновляющий маркер в cookie | `200`; `401` | все |
| `NFR-02` выход | `auth/logout` | `POST` — отзывает обновляющий маркер | `204` | пользователь |
| `NFR-04` готовность | `health` | `GET /health` | `200`; `503` база недоступна | все |

На все операции, кроме открытых, без маркера — `401`. Запрос к чужому или скрытому объекту — `404`, а не `403` (`NFR-02`).

## Решения

**Решение хоста и решение модератора — подресурс `decision`, а не два обработчика «подтвердить» и «отклонить».** Ресурс один — факт решения; различие в поле `result` (`confirmed` / `declined`, `approved` / `rejected`). Довод: два обработчика с почти одинаковым телом разойдутся при первом изменении.

**Очередь модерации — отдельный ресурс `host-verifications`, а не фильтр `GET /v1/hosts?status=pending`.** `GET /v1/hosts` открыт всем и отдаёт только проверенных. Фильтр по статусу на открытом ресурсе — защита перечислением: забытая проверка роли покажет непроверенных хостов всем.

**Повторная отмена — `200` с текущим состоянием, а не `409`.** Критерий S9, сценарий 3: «состояние не меняется, показан текущий статус». Повтор — нормальный случай при двойном нажатии, а не конфликт.

**Поиск — без маркера.** Владелец смотрит хостов до регистрации; в ответе нет контактов и адресов (`NFR-02`).

## Найдено при составлении перечня

| Находка | Что предлагается |
|---|---|
| Регистрация, вход и выход не следуют ни из одной истории S1–S10 — критерии начинаются с «хост авторизован» | Ирине: добавить функциональное требование «пользователь регистрируется и входит» |
| Хост должен видеть входящие запросы (S6), а владелец — свои брони; отдельной истории нет | Отнесено к `FR-05` и `FR-06`; подтвердить в требованиях |
| Истечение запроса без ответа хоста (48 часов) не следует из истории | Вопрос к сессии моделирования событий; при подтверждении — критерий в `FR-05` |
